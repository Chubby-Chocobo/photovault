# 0030 Google Drive import reads folder contents with drive.readonly

- **Status:** Accepted
- **Spec refs:** FR-119 (amended), FR-122 (amended), FR-123 (amended); supersedes the Google Drive scope and picked-folder parts of [0026](0026-cloud-folder-imports.md)
- **Review trigger:** Google changes what `drive.file` grants for a picked folder, the `drive.readonly` consent or verification rules change, or the owner wants imports that keep their sign-in after they finish

## Context

Decision 0026 shipped the import with `drive.file` only and listed the risk that a picked folder would not reveal its existing children. Version 0.3.0 confirmed it: the live log showed `files.list` for a picked folder answering 200 with an empty list, and the import "completed" with 0 files. Under `drive.file`, picking a folder grants the folder itself, not what is inside it.

## Decision

- **The import asks for two consents, one after the other, for the same account.** Google's desktop Picker guide says: "only the drive.file scope is permitted for these apps and it can't be combined with any other scope." The first 0.4.0 build sent `drive.file drive.readonly` with `trigger_onepick=true` and Google answered `Error 400: invalid_scope`. So:
  1. **Pick.** The authorization URL carries `drive.file` alone, with `trigger_onepick`, `allow_multiple`, `allow_folder_selection` and `prompt=select_account consent`. The app takes the picked ids, exchanges the code and reads the account (`about.get` with `user(emailAddress,permissionId)`). The `drive.file` token is then discarded; it is not revoked, because a revoke ends all of the client's grants for the account (see Consequences).
  2. **Read.** A plain OAuth (loopback, PKCE, no Picker parameters) asks for `drive.readonly` alone, with `login_hint` set to the account from step 1, `prompt=consent` and `access_type=offline`. The app checks that `drive.readonly` was granted, then that the signed-in account is the same one (the Drive `permissionId`, or the e-mail when either side lacks one; an account that cannot be read counts as different). Another account ends the import with `accountMismatch` ("choose the same account you used to pick the folder"). The refresh token kept for the import is this one; it is what lists and downloads. Cancelling either step records nothing.
  The owner sees a second Google consent; the app says "Step 2 of 2: allow reading the chosen folder" while it waits. `drive.readonly` lets the app list and download everything inside the folders the owner picked. The owner still chooses files and folders in the Picker; the app reads only the picked items and what is below picked folders, and only issues GET requests.
- **The backup destination keeps `drive.file` only.** Its sign-in, its scope check and its consent text do not change. A test pins both scope strings.
- **Recursion.** Picked folders are listed down to 64 folder levels (`DriveImportLister.maxDepth`); deeper folders are not listed and no error is shown. Listing uses `nextPageToken` paging and shared-drive flags. Docs, shortcuts, trashed items and files with an `appProperties` key starting `pv` are skipped. A file picked on its own and also found inside a picked folder is read once, under the deeper path. A folder picked and also inside another picked folder is walked once, under whichever root sorts first by Drive id.
- **The import grant is short-lived.** When an import is completed or cancelled and none of its files has an upload pending, uploading, deferred or missing at the destination, the app deletes its `import-<id>` Keychain item and drops its adapter. The engine names such imports (`closedImportsReadyToRelease`); the app deletes the items after each cycle, so a crash between the two is repaired by the next cycle. The same rule applies to Dropbox imports, because they use the same Keychain item and the same sign-in-again flow. A destination added later, or an upload repeated after the destination lost a file, asks the owner to sign in again through the existing "Đăng nhập lại" flow (FR-121); Google then shows the consent again.
- **Both permissions are required.** If the pick step does not grant `drive.file`, or the read step does not grant `drive.readonly` (Google shows the box and the owner may clear it), the sign-in is refused with a notice and nothing is stored (otherwise a picked folder would list as empty again).
- **Refreshing the import grant does not require `drive.file`.** The kept token is `drive.readonly` only, so `DriveImportAuth` refreshes without that scope check. Grants made by 0.4.0 or earlier hold `drive.readonly` plus `drive.file` or only `drive.file` and keep refreshing as before.
- **An empty import says so.** An import of any kind whose listing finds no photo or video ends as completed, with the reason "the folder had no photos or videos the app could read" in Settings, the notification and the activity line. In the Settings row only, a Google Drive import adds "import again from Settings › Nguồn › Nhập ảnh… › Từ Google Drive…", because an import made with 0.3.0 only had `drive.file`; the notification and the activity line carry the generic text. Names, ids and emails stay out of logs.

## Alternatives

- **Keep `drive.file` and ask the owner to select the photos inside the folder (⌘A).** Rejected by the owner (2026-11-10): easy to get wrong and silent when it is.
- **One consent with both scopes (the 0.4.0 build).** Rejected by Google: `invalid_scope` for the Picker.
- **Request `drive.readonly` for the backup destination too.** Rejected: the destination needs no read access outside its own files.
- **Keep the import grant after the import.** Rejected: a broad read grant for no purpose. The cost is one more sign-in when a destination is added later.

## Consequences

- The owner approves Google twice per import (and per "Đăng nhập lại" of an import). Both grants appear under the one app at myaccount.google.com/permissions. Both steps count towards the 100 refresh tokens per client and account.
- Google shows "See and download all your Google Drive files" on the import consent. `drive.readonly` is a restricted scope: the app stays unverified, which is fine for personal use (the owner clicks through the unverified-app warning). The owner must add the scope on the OAuth consent screen (Data access) in the Cloud Console.
- Imports made with 0.3.0 hold a grant without `drive.readonly`. They are not repaired: the owner imports the folder again. A new import gets a new id and does not collide with the empty one.
- A deferred upload that never recovers (for example a file too large for the disk) keeps the import grant until the owner cancels or the job ends.
- Only the token on this Mac is deleted. The `drive.readonly` permission stays in the Google account until the owner removes it at myaccount.google.com/permissions; the app does not revoke it (neither the pick step's `drive.file` token nor the read token), because a revoke drops all of the client's grants for that account, including a backup destination on the same account.
- Google Workspace accounts may be blocked from restricted scopes by their admin.
- The one-time cost of an extra sign-in when a destination is added after an import ended.
- **A signed-in import can wait for its turn.** The engine records a new import between sync passes, and a pass can last long (one large download). After both consents the sign-in row ends and the import is listed in Settings › Nguồn and the menu bar card as "Chờ đến lượt" (the same list for Dropbox imports); the real import then replaces it under the same id. The wait is an app-side entry; the engine's exclusive lane is untouched. Cancelling the entry cancels the start and deletes the stored sign-in; closing the Settings window does not, because the start runs in a task owned by the app model. A signed-in-again import shows "Đã đăng nhập · Chờ đến lượt" on its own row meanwhile. Several entries may wait, in order.
- **Limitation: a waiting import is lost if the app quits first.** Nothing about it is stored in the database, so it is not recorded and the owner picks the folder again. Its `import-<id>` Keychain item would be unreadable, so launch deletes every `import-` item that no import row names.
